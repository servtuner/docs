An experiment groups runs that differ in their knobs. The comparison ranks configurations and tells you whether the lead is real.

## Prerequisites

- Runs with the same workload, ladder, SLOs, arrivals and target type.
- At least three repeats per configuration for high confidence.

## Steps

1. Give every RunSpec the same `experiment` and set the value under test in `knobs`.
2. Apply each configuration to the target, then run its repeats. Managed vLLM is the only target servtuner changes for you.
3. Open **Experiments**, choose the experiment, pick an objective and select **Compare configurations**.

<Image src={shot} alt="Experiment page comparing three gateway concurrency values" />

The sample shows a mock server with three concurrency caps.

From the command line, pass analyzed bundles:

```sh
servtuner compare --bundles runs/a,runs/b,runs/c --objective slo_max_rps
```

## Read the comparison

| Result         | Meaning                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------- |
| Winner         | Its interval does not overlap the runner-up's. With single samples, the lead exceeds 10% |
| No winner      | The data does not separate the leaders. Add repeats                                      |
| Not comparable | Workload, ladder, arrivals, SLOs or target type differ                                   |
| Excluded run   | Its captured knobs contradict the declared ones, or a fault invalidated it               |
| Lower bound    | A run never failed an SLO. Extend its ladder                                             |
| Pareto set     | Configurations where improving one objective costs another                               |

The default objective is `slo_rps_per_gpu` for vLLM and SGLang, `slo_rps_per_core` for routers and `slo_max_rps` for OpenAI-compatible targets.

## vLLM or SGLang

An experiment may hold vLLM and SGLang runs of the same workload. They compare when they also serve the same model on the same, known hardware (GPU model and count) under the same SLOs: the server then becomes a varied knob, `server`, ranked with intervals like any other. A different model or hardware, or hardware servtuner could not capture, makes the pair not comparable, with the reason.

servtuner reads the hardware from the Kubernetes nodes the target's pods run on (`target.workload`). A target outside Kubernetes declares its machine in `target.hardware` (a host fills it in for saved and host targets); without it, its hardware is unknown. Only the GPU model and count must match: drivers, CPUs and hosts may differ, and GPU names match however they are written (`NVIDIA-GeForce-RTX-3070`, `NVIDIA GeForce RTX 3070`).

## Line runs up without ranking

Select two or more runs in the runs list, then **Compare runs**. The page aligns them by stage and knob. It does not declare a winner.

## Delete an experiment

An admin can **Delete experiment** on its page. It first lists what goes: its runs (each refused for the same reasons as [a single run](/guides/inspect-runs/#delete-a-run)), its analyses and its finished tuning sessions. Saved scenarios that use its runs block the delete unless you choose to delete them too. Managed targets and schedules are never touched. It cannot be undone.

## Verify

Check that each configuration lists the expected number of repeats and that no run is excluded unexpectedly.
