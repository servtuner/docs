servtuner installs as seven Helm releases, each on its own: cert-manager, CloudNativePG, Envoy Gateway and kube-prometheus-stack (each its upstream chart, unmodified), servtuner's private CA and a Gateway (plain manifests), and servtuner itself. You upgrade and roll back each one on its own, and skip any your cluster already runs. Each release's deploy bundle holds the helmfile that declares all seven and installs them in order, pinned to that release. [Components](/deployment/components/) explains each one: what it does, how to bring your own, and how to check it.

For a cluster with no internet access, follow [air-gapped installs](/deployment/air-gapped/) instead. It uses the same helmfile.

## Prerequisites

- Kubernetes 1.35 or newer, and a default StorageClass. For real benchmarks, GPU nodes with the NVIDIA device plugin.
- `helm` 3 or 4 and `helmfile` v1.8.5. `helmfile sync` needs no Helm plugin; `apply` and `diff` need helm-diff.
- Nodes that can pull from `ghcr.io`, where servtuner's images are published. Without internet access, follow [air-gapped installs](/deployment/air-gapped/).
- ReadWriteMany storage for several nodes, or an S3-compatible store. See [storage](/deployment/storage/).

## Steps

### 1. Download the deploy bundle

Download `servtuner-deploy-<version>.tar.gz` from the [release](https://github.com/servtuner/servtuner/releases), check it, and unpack it:

```sh
VERSION=<version>
base=https://github.com/servtuner/servtuner/releases/download/v$VERSION
curl -fsSLO "$base/servtuner-deploy-$VERSION.tar.gz" -O "$base/checksums.txt"
sha256sum --check --ignore-missing checksums.txt
tar -xzf "servtuner-deploy-$VERSION.tar.gz"   # writes deploy/
```

The chart in it defaults to the release's images, `ghcr.io/servtuner/servtuner-*:<version>`. To check signatures, see [verify downloads](/deployment/verify/).

### 2. Create Secrets first

No secret goes in a values file, the helmfile or the release. Values name a Kubernetes Secret, and you create it before the install.

| Secret                                                    | Where                               | Keys                           | When                                          |
| --------------------------------------------------------- | ----------------------------------- | ------------------------------ | --------------------------------------------- |
| A registry pull secret (`kubernetes.io/dockerconfigjson`) | Every namespace the releases run in | `.dockerconfigjson`            | Your registry needs a login to pull           |
| TLS certificates (`kubernetes.io/tls`)                    | servtuner's namespace               | `tls.crt`, `tls.key`, `ca.crt` | `tls.source: secret` instead of cert-manager  |
| Object store keys for model weights                       | The managed server's namespace      | Your names                     | Weights streamed from S3 without pod identity |
| A Hugging Face token                                      | The managed server's namespace      | `token`                        | Gated models from Hugging Face or a mirror    |

The chart generates the first-admin setup token itself. See [authentication](/deployment/authentication/).

### 3. Write your site values

Copy `deploy/helmfile/site-values.example.yaml` to `deploy/site-values.yaml`. Every value of the chart may go there, and it wins over the environment's values. The helmfile already points servtuner at its own issuer and Gateway; these are the values every site decides.

<Tabs syncKey="tls">
  <TabItem label="TLS with client certificates (default)">

```yaml title="deploy/site-values.yaml"
tls:
  enabled: true
gateway:
  hostname: servtuner.example.internal
storage:
  file:
    pvc: { create: true, accessMode: ReadWriteMany, size: 100Gi }
rbac:
  bench:
    targetNamespaces: [inference]
```

  </TabItem>
  <TabItem label="No TLS (a mesh encrypts)">

```yaml title="deploy/site-values.yaml"
tls:
  enabled: false
postgres:
  auth: password # a client certificate needs TLS
gateway:
  hostname: servtuner.example.internal
storage:
  file:
    pvc: { create: true, accessMode: ReadWriteMany, size: 100Gi }
rbac:
  bench:
    targetNamespaces: [inference]
```

`tls.enabled: false` states that something else, such as a service mesh or an encrypted CNI, encrypts this traffic. servtuner cannot check that. Without TLS, the API signs in to Postgres with a password.

  </TabItem>
</Tabs>

To use your own issuer, Gateway or Ingress instead of the helmfile's, see [components](/deployment/components/).

### 4. Install

```sh
helmfile -f deploy/helmfile.yaml.gotmpl -e eks sync
```

On a cluster without a load balancer, add `--state-values-set gateway.serviceType=ClusterIP` and reach the Gateway as in [try it on kind](#try-it-on-kind).

To use your own image registry, add `--state-values-set registry=registry.example:5000`. With a pull secret, also add `--state-values-set 'imagePullSecrets={regcred}'`.

### 5. Sign in

Open the hostname you set, create the first admin with the setup token, and sign in. See [authentication](/deployment/authentication/).

## Try it on kind

The `kind` environment is a complete trial on a local kind cluster, with servtuner's defaults (TLS with client certificates). It needs no site values.

```sh
kind create cluster --name servtuner-trial
helmfile -f deploy/helmfile.yaml.gotmpl -e kind sync
kubectl -n servtuner wait --for=condition=Ready pod -l app.kubernetes.io/component=api --timeout=10m
kubectl -n envoy-gateway-system port-forward \
  "$(kubectl -n envoy-gateway-system get svc -l gateway.envoyproxy.io/owning-gateway-name=servtuner -o name)" 8080:80
```

Open `http://localhost:8080`, and create the first admin with the setup token:

```sh
kubectl -n servtuner get secret servtuner-setup-token -o jsonpath='{.data.token}' | base64 -d
```

To change a value, put it in `deploy/site-values.yaml`, which comes after the kind values, and run `sync` again. Remove the trial with `kind delete cluster --name servtuner-trial`.

## Skip a prerequisite

Turn off any prerequisite your cluster already runs:

```sh
helmfile -f deploy/helmfile.yaml.gotmpl -e eks \
  --state-values-set install.certManager=false,install.prometheus=false sync
```

servtuner then uses yours. [Components](/deployment/components/) lists what each one needs: cert-manager's CRDs, an issuer that writes `ca.crt`, the CloudNativePG operator (or an external Postgres), Envoy Gateway with the Backend API (or your Ingress), and your Prometheus (`prometheus.url`).

When your cluster already runs every prerequisite, install the chart alone from the registry:

```sh
helm install servtuner oci://ghcr.io/servtuner/charts/servtuner --version <version> \
  --namespace servtuner --create-namespace -f site-values.yaml
```

## Expose it

<Tabs>
  <TabItem label="Gateway API">

`gateway.enabled` renders two HTTPRoutes on one hostname: the UI, and the API under `<basePath>/api`. With TLS, an Envoy `Backend` presents the chart's client certificate to the API and a `BackendTLSPolicy` checks the API's name. The helmfile's Envoy Gateway has the Backend API on, and its `servtuner-gateway` release provides the Gateway.

  </TabItem>
  <TabItem label="Ingress">

`ingress.enabled` renders the same two routes as Ingresses for ingress-nginx, which is retired upstream: prefer the Gateway API for new installs. With TLS, the API Ingress verifies the API with the chart's certificate. `ingress` and `gateway` are exclusive. The helmfile installs no Ingress controller, so running yours is up to you.

  </TabItem>
</Tabs>

For a subpath, set `frontend.basePath`. Terminate browser TLS at the gateway or ingress. `networkPolicy.enabled` (the default) lets only the ingress controller or gateway (`networkPolicy.ingressController`) and bench Jobs reach the API, and nothing reach a bench pod. It needs a CNI that enforces NetworkPolicy.

## Permissions

The API manages Jobs, ConfigMaps and Secrets in the runs namespace. bench reads workloads in `rbac.bench.targetNamespaces` and nodes cluster-wide. Nothing is granted for managed targets until you list `rbac.tuning.namespaces`.

## Upgrade

Run `helmfile … sync` again with the new versions. The API migrates its database on start. Each release is an ordinary Helm release, so `helm history` and `helm rollback` work on each. To upgrade only servtuner and hold the prerequisites, add `--selector name=servtuner`.

## Verify

```sh
helmfile -f deploy/helmfile.yaml.gotmpl -e eks list   # the releases and their versions
kubectl -n servtuner get pods
kubectl -n servtuner get certificates
kubectl -n servtuner get gateway servtuner   # PROGRAMMED True
```

Then save a target and run a connection check.
